# How translation works

For contributors: how [protocol translation](translation.md) is built, where
its data comes from, how it is tested and how to add a version.

## How it works

`crates/rift-translation` is a library without I/O. A `Translator` chains one
step per pair of adjacent protocols (41 pairs between 1.12 and 26.3). Each
pair has an `up` step for a newer client on an older backend and a `down` step
for the reverse.

- **Steps** route packets by name. A packet both protocols share passes
  through with only its ID changed. A step may rewrite, split, drop, answer or
  synthesize packets, which the 1.20.2 configuration phase, the 1.13
  flattening and the 1.20.5 item components need.
- **Parsing.** A packet a step has to change is parsed completely. One it
  cannot parse fails the connection rather than reaching the peer corrupted.
- **Shared codecs** under `src/codec/` know, in every protocol, the structures
  that travel in many packets and versions: item stacks before and after data
  components, entity data, particles, chunks and light, text components as
  JSON and NBT, tags, command trees and synchronized registries. They convert
  between the two protocols of whichever step calls them.
- **Registry IDs** are mapped by entry name through tables built from each
  version's own registries, with the per-pair rename and stand-in rules.

In Rift, a backend on another protocol gets a translator inside its
connection. The session then sees a backend that speaks the player's protocol,
so login, forwarding, switching, the tab list, proxy commands and everything
plugins do work the same with and without translation. Packets Rift neither
translates nor rewrites are still forwarded in the frame they arrived in.

## Cost

Cost grows with the distance between the two versions, because every step in
between handles each packet. A release build replays a whole recorded join
session through all 41 steps in about two seconds of CPU, and through one step
in about 0.15 seconds including start-up.

A 1.21.1 or older client on a 1.21.2+ backend costs more at join: its recipe
list is resent whenever the book grows.

## Where the data comes from

Rift is BSD-licensed and ships no ViaVersion code or mapping files. ViaVersion
and ViaBackwards served as references for what changed between versions; the
implementation was written independently.

| Data | Source |
| --- | --- |
| Per-version packet tables, registries and block states | Generated by [`scripts/translation_crate.py`](../scripts/translation_crate.py) from the pinned, checksum-verified official servers in [`tests/servers.json`](../tests/servers.json) (Mojang's data generator reports). For versions that predate those reports, from the MIT-licensed [PrismarineJS minecraft-data](https://github.com/PrismarineJS/minecraft-data). |
| Packet order for versions before 1.21 | ViaVersion's packet-type enums, which is the protocol's own numbering under Mojang's names. |
| Entity data layouts, vanilla tags and the registries servers synchronize | Extracted from the same server jars by `scripts/translation_entities.py`, `translation_tags.py` and `translation_registries.py`. |

[`data/SOURCES.md`](../crates/rift-translation/data/SOURCES.md) lists the
source of every table. Every script has a `--check` mode that fails when the
committed files are stale.

## Verification

| Check | What it does |
| --- | --- |
| Unit tests | Over 750 in the crate cover every codec and step, with recorded packets from the official server of each version where a hand-built one would prove less. |
| Recorded sessions | [`tests/translation_corpus.py`](../tests/translation_corpus.py) records a scripted session from the official server of every protocol. The crate's `replay` example feeds one through any chain of steps. Every pair, and the whole range in both directions, replays without a rejected packet. |
| Real servers | [`tests/translation_matrix.py`](../tests/translation_matrix.py) starts a real server, connects a reference client directly and a client of another version through the translator, and runs 33 scenario steps (blocks, items, entities, chat, commands, containers, scoreboards, titles, respawn, a dimension change and more). |
| Real clients | [`tests/real_client.py`](../tests/real_client.py) runs the unmodified vanilla client of a version headlessly through the translator and fails on any packet, registry or network error it logs ([details](../tests/REAL_CLIENT.md)). Real clients of every anchor version were run against older and newer servers of their neighboring versions. |
| Through Rift | `tests/translation_matrix.py --via rift` and `--via rift-detect` run the same cells through the `rift` binary, with the backend's version declared and detected. [`tests/translation_minecraft.py`](../tests/translation_minecraft.py) and [`tests/translation_network.py`](../tests/translation_network.py) switch a player between backends of different versions. [`tests/translation_real_client.py`](../tests/translation_real_client.py) runs real vanilla clients behind Rift while the server's console plays a scenario. |

The real-server matrix decodes every packet the translated client receives
strictly with the pinned minecraft-data schema of its own version, and
compares it with what the reference client saw. The schema is an independent
description of the protocol, with documented corrections where the official
server disagrees with it.

Every adjacent pair passes in both directions on the official server, as do
Paper, Spigot and Pumpkin fixtures.

```sh
python3 scripts/translation_crate.py --check
cargo test -p rift-translation
cargo run -p rift-translation --example replay -- --backend 340 --client 777 --summary
python3 tests/translation_matrix.py --accept-eula --server vanilla-1.16.5 --client 1.12.2,1.20.1,26.3 --via rift
python3 tests/real_client.py --accept-eula join --version 1.20.1 --address 127.0.0.1:25565
```

These checks use offline-mode servers and offline test accounts. They do not
replace playing with a signed-in graphical client on your own network, and
they cover the vanilla protocol: a plugin or mod that sends its own packet
layouts through plugin channels is passed through as it is.

## Add a version

1. Add the release to `tests/servers.json` and `version::PROTOCOLS`, and
   generate its data with the scripts above.
2. Create the pair's module under `src/steps/` with an `up` and a `down` step
   built on `RouteBuilder::defaults()`; the module documentation of
   `src/steps/mod.rs` describes how. `Routes::problems()` lists every packet
   that still needs a rule.
3. Teach the shared codecs the new protocol's layouts where they changed, and
   write the pair's rename and stand-in rules
   (`cargo run -p rift-translation --example mapping_report -- <older> <newer>`
   lists what is unmapped).
4. Record the new server's session, then run the replay, the matrix and a real
   client for the new pair in both directions.
